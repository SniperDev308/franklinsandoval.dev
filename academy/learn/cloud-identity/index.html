01 / IDENTITY

Authentication is a dependency chain

User→Identity→Authentication→Authorization→Resource

For support work, separate “who are you?” from “what are you allowed to access?” A successful sign-in does not automatically prove authorization to every resource.

02 / MICROSOFT 365 SUPPORT

Reduce the scope before changing anything

User scope

One user, a group, or the whole organization?

Identity state

Account status, authentication outcome and relevant access conditions.

Service scope

Is the issue isolated to one workload or present across services?

Client vs service

Compare browser, client application and another known-good endpoint when appropriate.

03 / AWS FOUNDATION

Compute is only one layer

EC2

Virtual compute instances that still depend on OS health, networking, applications and access configuration.

VPC

The logical network boundary containing subnets, routes and other networking components.

Security groups

Control allowed traffic associated with supported AWS resources. Treat them as part of the connection path.

IAM

Identity and access controls for AWS resources and actions.

04 / CLOUD NETWORKING

The packet did not disappear because the server moved to cloud

Client → DNS → network path → VPC/subnet → security policy → instance → OS firewall → listening service → application

The same reasoning from Networking II survives. Cloud adds control planes and policy layers, but an application still needs a valid end-to-end path.

05 / OBSERVABILITY

CloudWatch: evidence before assumptions

Amazon CloudWatch provides monitoring and observability signals for AWS resources and applications. In a support workflow, use metrics, logs and alarms to correlate the reported symptom with resource or application behavior before changing configuration.

SUPPORT REFLEX

A running EC2 instance does not prove the application is healthy. Correlate reachability, service state and available monitoring evidence.

06 / SUPPORT LAB

Two fault trees

  1. Draw a Microsoft 365 sign-in path from user to protected resource.
  2. Create branches for authentication success/failure and authorization success/failure.
  3. Draw an AWS web application path from client to an EC2-hosted service.
  4. Include DNS, route, security group, OS listener and application.
  5. Create one failure at each layer.
  6. For every failure, write the smallest test that proves or disproves it.
