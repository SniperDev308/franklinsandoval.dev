MISSION OBJECTIVEBuild a practical conceptual model of Niagara stations, drivers, networks, points, histories, alarms and tagging for BMS troubleshooting.

01 / ARCHITECTURE

Think in layers, not screens

Supervisor / UI→Station→Driver / Network→Device→Point

A Niagara station is a running software environment containing components and services. For support reasoning, determine whether the problem belongs to the station, a driver/network, one device, or an individual point.

02 / DRIVERS + POINTS

Protocol data enters through a driver

Driver / network

Represents integration with an external protocol or system, such as a BACnet network.

Device

Represents an integrated controller or equipment endpoint beneath that network.

Point

Represents exposed data used for monitoring, logic, history, alarm or command workflows.

Scope

If every device under one network fails, investigate differently than when one point on one device fails.

03 / HISTORIES + ALARMS

Preserve the story of the system

Histories let operators inspect behavior over time. Alarm services organize exceptional conditions and events. Together they turn a snapshot into a timeline that can support root-cause reasoning.

SCENARIO

A temperature point appears normal now, but an alarm occurred at 02:14. The history shows a sharp rise followed by recovery.

Which view tells you more about what actually happened?
Reveal reasoning

The event plus historical context. Current state alone cannot reconstruct the sequence that produced the alarm.

04 / TAGGING

Give components searchable meaning

Tags and semantic relationships can describe what a component represents and how it relates to equipment or systems. At scale, this makes navigation, queries and analytics more useful than relying only on folder names.

05 / TROUBLESHOOTING

Collapse the fault domain

1. Is the station healthy and reachable?

2. Is the affected driver/network operational?

3. Is the issue all devices or one device?

4. Is the device reachable at the underlying protocol/network layer?

5. Are all points affected or one point?

6. What do histories and alarms show before the failure?

7. What physical verification is required?

06 / ARCHITECTURE LAB

Build a Niagara fault tree

  1. Draw one station containing a BACnet network.
  2. Add three BACnet devices: AHU-01, CDU-01 and CH-01.
  3. Add at least four points beneath AHU-01.
  4. Mark one point as historized and one as alarm-enabled.
  5. Create three failure scenarios: entire network offline, one device offline, one point stale.
  6. For each scenario, write the smallest first test that separates it from the other two.
  7. Identify where BACnet/IP troubleshooting from Week 05 enters the workflow.
